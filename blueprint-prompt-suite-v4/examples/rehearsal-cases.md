# Bounded integration rehearsal

**Suite:** `harmonized-v4` · **Date:** 2026-09-08  
**Evidence type:** Author-only analytical walkthrough of constructed cases. The release checker runs the arithmetic and set/graph calculations noted below. No model has executed the six-stage workflow or these assignments.

These are narrow policy fixtures, not complete conformant systems-design, architecture, or PRD packages. A conditional expected status assumes the other applicable obligations have passed; that premise is not evidence that any real package passed. Use valid cases as well as defects when testing agents.

## Fixture A — tiny direct assignment

A user supplies an existing controlled README and delegates an exact wording replacement, with its allowed file boundary and a direct before/after comparison. Meaning, shared contracts, product behavior, approvals, and external effects do not change. The complete local design and evaluation already exist. No upstream planning question remains.

## Fixture B — three related territories

A handles sample intake, B computes a summary, and C presents the accepted summary. One canonical contract, `IF-1`, owns sample units, sequence meaning, error behavior, and version compatibility. Each territory owns local details; one integration owner owns the joined intake → summary → display outcome. Recovery and integrated acceptance remain explicit shared duties. Required implementation outputs may follow accepted predecessor gates; the shared definition must exist before dependent design.

The resource fixture allows A, B, and C to run concurrently from one pool of 100 units. The deliberately defective allocation gives each 40 units. The corrected case gives each 30 units. This is a constructed capacity constraint, not a measured system.

For scope allocation, let parent duties be `{ingest, display, recovery, integrated-acceptance}`. A deficient split assigns only `{ingest, display}`. A valid split explicitly retains `{recovery, integrated-acceptance}` with accountable owners and gates.

For the change-impact calculation, the declared dependency graph is:

```text
contract -> A, B, C, integrated
A-local -> A
A -> recipient-A
B -> recipient-B
C -> recipient-C
```

`A-local` here means a local packet clarification that changes neither shared behavior nor assumptions of integrated evidence. A real change needs its real dependency map; this fixture cannot prove that a production change has only these effects.

### R14 — path change is not always administrative

### R15 — executor editions and earlier valid evidence

Then change only the suite version or permitted presentation of an older packet. **Expected:** Preserve the same gates, scope, review requirements, and protected acceptance rules; do not demand new formatting or repeat valid upstream review solely because the version changed. **Walkthrough:** The checker compared the shared executor sections listed in the validation notes. This is textual agreement, not proof of identical model behavior.

## Use in the first actual trials

Freeze task inputs, governing prompt files, chosen model/profile, tools, available context, permissions, and the intended fresh-recipient arrangement before each run. Provide the fixture and assigned question without the expected answer to a reviewer whose detection or freshness is being tested. Retain this answer key with the evaluator.

Record supported defects found, missed duties, false findings, required rereading, author interventions, unnecessary invalidation, actual context interruptions, and effort spent on coordination rather than product work. Keep analysis, observed model behavior, implementation results, and acceptance separate. A test that blocks every case fails the valid controls; one that passes every case misses the deliberately broken ones.

A later large-package comparison is still needed. This walkthrough and its small calculations do not establish improved model performance, full semantic conformance, independent qualification, or production readiness.
