# Bounded-review assignment example

**Applies to:** v4 design/review suite. **Status:** Optional usage example, not an additional mandatory artifact or new authority source.

A lead can place the following information in an existing assignment or review note. Fill actual values or exact accessible references. Size the assignment by the material the reviewer must consider together, not by this template's length. A reviewer may retrieve the named canonical sections; the lead must include all governing conditions and exceptions relevant to the question.

## Assignment

**Question and scope:** Review `<one local contribution, both sides of a material boundary, or one spanning outcome>`. Assess `<named obligations>` against `<candidate and relevant contract revisions>`. Explain the limits of this claim; identify the parent contribution and work that this unit does not cover.

**Authority and effects:** Read-only subject. Inspect `<allowed files/repositories>`. Run `<authorized checks, if any>` in `<permitted environment>`. Do not repair canonical sources, change scope or acceptance, call external services, or grant approval through this assignment. Return an owner-routed finding when the needed change exceeds these limits.

**Required reading and capacity:** Start at `<entry point>`. Read `<exact governing clauses and local sections>` now; retrieve `<canonical contracts, counterpart obligations, and evidence>` for the named checks. `<history>` is background unless a conflict requires it. Preserve required context and exceptions. Assess instructions + subject + shared detail + evidence + tool results + working/output reserve. Record actual lookups and any mismatch; do not drop a rule to fit.

**Checks:** State the expected property and supporting source. For a boundary, examine the same canonical rule and both sides' obligations together; test provider guarantees against consumer assumptions. For a spanning outcome, examine combined constraints and the joined scenario, not just local passes. Test the strongest reasonable rebuttal before confirming a material defect. Distinguish an analytical counterexample, executed observation, specification gap, and untested concern.

**Return:** Provide the exact subject and source revisions; obligations and relationships actually examined; substantive conclusion and evidence; supported findings, rebuttals, and affected owners; unresolved or unreviewed scope; and the next bounded check. Do not return only “PASS.” A cross-scope concern needs evidence and an owner, not silent scope expansion.

**Integration:** The lead checks returned assumptions and guarantees against the relevant canonical rules, joins results only across compatible bindings, and assigns affected counterpart or outcome checks. It need not repeat every local inspection. A report on a demonstrated missing prerequisite can complete assessment of that gap, but cannot satisfy the missing check or close an unverified repair.

## Fresh-recipient variant

For PRD consumption, use the recipient questions in [PRD author v4](../05-PRD-implementability-authoring-prompt-v4.md) or [PRD reviewer v4](../06-PRD-implementability-adversarial-review-prompt-v4.md), which contain the same rule. Provide only the actual worker packet, declared access, applicable effect limits, and the consumption assignment. Do not include this example's analytical findings, prior answers, author-only history, or solution coaching in a supposedly fresh test.

Plan the exposure boundary before intake. Record freshness and coverage per slice, including material retrieved through tools. The recipient may navigate sources the worker can access. Batching is allowed, but a sample does not cover omitted slices and an earlier substantive repair may remove freshness for later dependent checks. The recipient does not need to implement the product to show that it can use the packet.

No separate agent per file, metadata service, fixed context percentage, or private reasoning transcript is required.
